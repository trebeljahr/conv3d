A pass through the failure modes you're most likely to hit, and what each one tells you.

## Start with `conv3d doctor`

If anything looks off, run:

```bash
conv3d doctor
```

You'll see something like:

```
conv3d  1.0.5
node    v24.4.0
platform darwin-arm64
cwd     /Users/you/project
install /usr/local/lib/node_modules/conv3d

dependencies:
  obj2gltf         declared ^3.1.6   installed 3.1.6
  gltf-pipeline    declared ^4.1.0   installed 4.1.0
  fbx2gltf         declared ^0.9.7   installed 0.9.7
  gltfjsx          declared ^6.5.3   installed 6.5.3
  commander        declared ^14.0.2  installed 14.0.2
  inquirer         declared ^12.10.0 installed 12.10.0
  fast-glob        declared ^3.3.3   installed 3.3.3
```

Read each line:

- **`conv3d`** — installed version of the CLI.
- **`node`** — your Node runtime. Must be `v24` or higher (see below).
- **`platform`** — `${process.platform}-${process.arch}`. Only `darwin-*` and `linux-*` are supported.
- **`cwd`** — where you ran the command from.
- **`install`** — where conv3d itself lives on disk. Useful when something resolves a different copy than you expect.
- **`dependencies`** — each row shows the declared range vs. the actually-installed version.

A row whose installed column reads `not found` means the dependency is missing from disk. That's almost always a broken install — reinstall and try again:

```bash
npm install -g conv3d
```

For machine-readable output:

```bash
conv3d doctor --json | jq '.dependencies[] | select(.installed == null)'
```

`doctor` always exits `0`, even when deps are missing. Inspect the report, don't rely on the exit code.

## Node version mismatch

conv3d requires **Node.js 22 or newer**. The `engines` field in `package.json` is `>=22`; local validation passes on both Node 22.20.0 and Node 24.14.1.

**Symptom**

`npm install -g conv3d` warns or refuses with an engines error:

```text
npm WARN EBADENGINE Unsupported engine
npm WARN EBADENGINE   required: { node: '>=22' }
npm WARN EBADENGINE   current: { node: 'v20.x.x', npm: '...' }
```

If the package is already on disk, the CLI may also exit immediately with a Node syntax/runtime error before any conv3d output appears.

**Cause**

Your active `node` binary is older than the runtime conv3d declares in `package.json`.

**Fix**

Check your active version:

```bash
node --version
```

Upgrade with `nvm`, `fnm`, Homebrew, or whatever you use, then reinstall conv3d.

```bash
npm install -g conv3d
```

## Windows is unsupported

conv3d's `package.json` declares `"os": ["darwin", "linux"]`. The blocker is `fbx2gltf` — its native binaries don't ship for Windows.

If you must run conv3d on a Windows host, use WSL2 (Ubuntu / Debian) and install conv3d inside the Linux environment, not on the Windows side.

## Apple Silicon needs Rosetta for FBX

`fbx2gltf` ships an Intel macOS binary. On Apple Silicon Macs, macOS runs that binary through Rosetta 2.

**Symptom**

OBJ and glTF inputs work, but FBX conversion fails on `darwin-arm64` with a native-binary launch error such as:

```text
Bad CPU type in executable
```

or:

```text
spawn .../node_modules/fbx2gltf/bin/Darwin/FBX2glTF Unknown system error -86
```

**Cause**

The bundled `fbx2gltf` executable is `x86_64`, not `arm64`, and Rosetta is not installed or not available to the process.

**Fix**

Install Rosetta once, then rerun the same conv3d command:

```bash
softwareupdate --install-rosetta --agree-to-license
```

No conv3d reinstall is usually needed. Confirm the platform line with:

```bash
conv3d doctor
```

## Linux glibc / libstdc++ mismatch

The Linux `fbx2gltf` binary is an x86-64 glibc binary. It is not a musl/Alpine binary.

**Symptom**

FBX conversion fails before `fbx2gltf` can print normal converter output. On older glibc images, the error names a missing symbol version:

```text
.../node_modules/fbx2gltf/bin/Linux/FBX2glTF: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.15' not found
```

The same binary also requires a recent enough C++ runtime. Older distributions can report:

```text
.../node_modules/fbx2gltf/bin/Linux/FBX2glTF: /usr/lib/x86_64-linux-gnu/libstdc++.so.6: version `GLIBCXX_3.4.21' not found
```

On musl-based images such as Alpine, the dynamic loader is missing instead; Node often surfaces that as:

```text
Error: spawn .../node_modules/fbx2gltf/bin/Linux/FBX2glTF ENOENT
```

**Cause**

The packaged converter is dynamically linked against glibc. The binary advertises `/lib64/ld-linux-x86-64.so.2` as its loader and needs at least `GLIBC_2.15` plus `GLIBCXX_3.4.21` from `libstdc++`.

**Fix**

Run conv3d in a glibc-based Linux environment with a new enough runtime. Debian 8+, Ubuntu 14.04+, current GitHub Actions Ubuntu images, and current Debian/Ubuntu containers are fine. Avoid Alpine for FBX conversion unless you provide a compatible glibc layer and matching `libstdc++`.

Check your host:

```bash
ldd --version
strings /usr/lib/x86_64-linux-gnu/libstdc++.so.6 | grep GLIBCXX_3.4.21
```

If those checks fail, switch base images or upgrade the OS package that provides glibc/libstdc++.

## FBX → magenta 1×1 placeholder

**Symptom**

You convert an FBX, load the `.glb` in three.js, and the mesh is solid pink or uses a 1×1 magenta placeholder texture.

**Cause**

The FBX referenced texture paths that `fbx2gltf` could not resolve.

**Fix**

conv3d already runs a recovery pass after every FBX conversion. For the full symptom, cause, and recovery flow, see [FBX texture recovery](./textures) instead of duplicating it here.

## Glob matched zero files

```
⚠️ Glob matched no files: ./assets/**/*.fbx
```

The process **exits `0`** with an empty result object. This is intentional — agent globs that legitimately match nothing shouldn't be errors. If you want a hard failure, check `converted.length` yourself:

```bash
result=$(conv3d bulk "./assets/**/*.fbx" -m ALL -y --json)
if [ "$(echo "$result" | jq '.converted | length')" -eq 0 ]; then
  echo "no matches" >&2
  exit 1
fi
```

Directory mode behaves the same — `⚠️ No suitable models found in <dir>` also exits `0`.

## Exit code `2` — per-file failures

Exit `2` means the run completed, but at least one file failed. `converted[]` lists the successes, `errors[]` lists the failures:

```bash
result=$(conv3d bulk ./models -m ALL --tsx -y --json) || true
echo "$result" | jq '.errors[] | "FAILED: \(.file) — \(.message)"'
echo "$result" | jq '.converted | length'
```

Each entry in `errors[]` is `{ "file": "...", "message": "..." }`. Retry only the failed files, not the whole batch.

Exit code summary:

| Code | Meaning |
|---|---|
| `0` | Success — including empty glob matches. |
| `1` | Fatal: bad args, missing input, unsupported model type. JSON has `{ ok: false, error }`. |
| `2` | Partial: some files failed. JSON has `errors[]` populated. |

## File-exists conflicts default to `skip`

In non-interactive mode (`-y`, or any time stdin isn't a TTY), conv3d **skips** outputs that already exist. They show up in `skipped[]`, not `errors[]`, and the exit code is still `0`.

If you're re-running a build and wondering why nothing changed, that's why. Force overwrite explicitly:

```bash
conv3d bulk ./models -m ALL --tsx --optimize -y -f --json
# or:
conv3d bulk ./models -m ALL --tsx --optimize -y --overwrite=replace --json
```

Interactive mode defaults to `ask` (prompts for each conflict). To make a script idempotent, always pass `--overwrite=replace` (or `-f`).

## Banner gone — optional deps missing

The rainbow `conv3d` banner needs two `optionalDependencies`: [`figlet`](https://www.npmjs.com/package/figlet) and [`lolcatjs`](https://www.npmjs.com/package/lolcatjs).

**Symptom**

`conv3d` runs normally, but the large rainbow banner is gone. If you inspect the global install, the optional banner packages are missing:

```text
figlet@^1.5.2 missing
lolcatjs@^2.4.3 missing
```

**Cause**

You installed with `--omit=optional`, set npm to omit optional dependencies, or your package manager skipped optional packages. conv3d treats the banner as cosmetic and suppresses it when those modules are unavailable.

**Fix**

The CLI is still working. No fix is required for scripts, CI, agent runs, `--json`, or conversions.

To get the banner back, reinstall with optional dependencies enabled:

```bash
npm install -g conv3d   # default includes optionals
```

The banner is also suppressed (intentionally) when stdout isn't a TTY, or when any of `--help` / `--version` / `--quiet` / `--json` is passed — agents and pipes never see it.

## Still stuck?

Open an issue with `conv3d doctor --markdown` pasted in:

```bash
conv3d doctor --markdown
```

That gives the maintainers the exact versions, platform, and dependency state of your install in a paste-ready block — everything needed to reproduce the bug. File at [github.com/trebeljahr/conv3d/issues](https://github.com/trebeljahr/conv3d/issues).
